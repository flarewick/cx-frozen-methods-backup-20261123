## 2. 一次查询中如何工作

1. 原冻结 VLA 根据当前观测和指令，使用原采样器与本场景 RNG 生成 `32×14` 的 base 动作块。共享 adapter 提出 ARM 方向残差，GRIP 残差为零。
2. `EventDetector` 按原因果规则识别夹爪开/合及确认反转事件。当前 `enable_progress=False`，不启用 progress-mismatch 事件。
3. 原 `LocalController` 为新事件构造当前合法 packet 和事件/介入上下文，调用 `AllCandidateVeto` 中的同一个冻结 v118。
4. 门控按原 `rescue - 2*harm > 0` 判定。拒绝会结束本次事件，不关闭后续事件的评分资格；新事件仍可重新判断。
5. 允许的候选还必须满足原冷却、待处理队列和每局介入预算。候选若因冷却进入队列，在实际取出时使用**届时的新观测、新候选与新上下文**再次评分；不重放旧动作块。
6. 最终允许时只对一个 action chunk 施加 ARM 修正，执行原官方逐动作控制/物理时钟/成功回调。之后至少有一个 base-only 冷却查询。每局最多施加三次修正。

简化伪代码（真实实现以锁定源码为准）：

```python
# 每次查询先生成当前 base 和候选，再经过原检测器/控制器
packet = candidate_packet(current_legal_inputs, raw_delta)
event, evidence = detector.step(query, packet)

def shared_score(current_packet, current_context):
    return frozen_v118.predict(model, current_packet, current_context)

decision = original_controller.step(
    query, event, packet, shared_score, enabled=True
)
# 最终激活仍由原预算/冷却/FIFO/TTL约束决定
applied_delta = 0.5 * raw_arm_delta if decision['active'] else zero_delta
```

“全事件”指**原控制器的每个合法评分机会**，包括新事件与待处理候选的重新评分；不是每个物理步都纠正，也不是跳过资格/预算强行对所有动作评分。新事件可能先评分、后因预算耗尽而无法执行，因此否决记录数不等于实际减少的纠正次数。

与旧首次门控的唯一科学差异，是去掉 `query != first_scored_query` 时回退原 always-admit scorer 的分支。`first_scored_query` 仍保留作日志标记，不再限制评分范围。adapter、方向残差、阈值、控制器和执行器均保持。

## 4. 门控能看到哪些输入

- 当前合法观测特征、指令特征、命令状态和运动学表征。
- 当前 base 动作块和当前具体候选的 ARM 方向/幅度表征；沿用既有 593 维特征实现。
- 原 `event_context` 的 8 个数：五类事件标识、事件年龄、已接受介入次数、距离上次介入的查询间隔。年龄与次数按原代码截断/归一化。
- 真实后续观测会反映先前执行结果；控制器也保留真实介入、冷却及排队状态。

这里没有新增 RNN 或完整的历史接受/否决序列编码。显式上下文主要记录介入次数与时间等状态，不能把它描述为学习到了任意长度的介入历史。

策略不能读取场景成败、未来轨迹、任务/seed 标签、物体真值位姿、接触真值或审计标签。离线完整物理轨迹只用于审计与分析，不作为门控输入。现有 EVAL 结果不转作 TRAIN 逐事件监督。
